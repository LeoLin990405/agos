## 零、先说一件对主控自己不利的事：本轮踩了一脚，破坏的是 tracked 基线

按第三轮定下的规矩，这类事放在文件最前面，因为它直接影响审查者该怎么读后面的每一条。

**这不是假想缺陷，是本轮主控本人在执行过程中真实踩到的，有完整复现和留证。**

### 0.1 发现

`scripts/acceptance/measure-dependency-surface.mjs` **静默吞掉未知参数**。

主控想看一眼当前的依赖面指纹，敲了：

```sh
node scripts/acceptance/measure-dependency-surface.mjs --print
```

该脚本**从来没有** `--print` 这个标志。

### 0.2 最小复现与后果

参数解析长这样（修复前）：

```js
const opt = (name, dflt) => {
	const hit = args.find((a) => a.startsWith(`--${name}=`))
	return hit ? hit.slice(name.length + 3) : dflt
}
const outPath = opt('out', join(REPO_ROOT, 'scripts/acceptance/dependency-surface.json'))
```

`opt()` **只认 `--name=value` 一种形态**。`--print` 匹配不上任何一个 `--<name>=` 前缀，
于是它既不报错、也不生效，**一声不响地落空**。

致命之处在于**默认输出路径就是 tracked 文件**
`scripts/acceptance/dependency-surface.json`。所以实际发生的是：

1. 操作者以为在做一次**只读打印**；
2. 脚本按默认路径跑完了**全量测量**（本轮实测约 6.5 分钟）；
3. 结束时**覆写了版本控制里的基线**——`git diff` 显示 **471 增 / 338 删**。

**更糟的一层**：当时四个实施代理正在并行改源码。那次测量观测的是**移动靶**，
所以被写进去的数据**本身也不可信**——它既破坏了基线，又没有产出任何有效替代品。

### 0.3 处置与留证

- 已 `git checkout` 还原。还原后 `inputsDigest` = `02046c1ef77d…`，与 phase3 记录**一致**；
- 误测量产物**留证**在本轮日志目录：`logs/controller-accidental-surface-measurement.json`，sha256 `2f4e555c8533d888edd00f0f2036bb053d9053fb047ecaa5550cdd8a066b7e43`。

### 0.4 修复

在**参数解析处**校验，未知参数一律 **exit 78** 并打印合法参数与危害说明：

```js
const LEGAL_VALUE_FLAGS = ['out', 'plugin', 'logdir']
const LEGAL_BARE_FLAGS = ['--no-shield']
```

合法参数**只有** `--out=` `--plugin=` `--logdir=` `--no-shield`，此外一概拒绝。

**为什么校验放在解析处而不是写盘前**：放在写盘前也能防住覆写，但要**先烧掉六分半钟**
才告诉操作者"你打错了"。校验的价值一半在于"别做错事"，另一半在于"早点说"。

**为什么错误信息里要写危害**：光说"未知参数"，操作者会以为只是拼错了重敲一次即可，
不会意识到**旧版本下这一敲会覆写仓库基线**。所以 stderr 里直接给出两条替代路径：
只想看内容用 `node -e` 读文件，想测量但不动基线用 `--out=<临时路径>`。

### 0.5 关闭依据（否证，不是"现在绿了"）

`selftest.mjs` 新增三条负控：

| 负控 | 打什么 | 断言 |
|---|---|---|
| **NC21** | `--print` / `--outt=/tmp/x` / `--noshield` / `bogus` / `-o` 五种形态 | 每种都 exit **78**、stderr 点名"无法识别的参数"、**且在任何测量输出之前退出**；循环结束后断言 tracked 基线**一个字节都没变** |
| **NC21b** | 裸 `--out /tmp/…`（空格分隔，无 `=`） | exit 78；tracked 基线一字节未变 |
| **NC21c** | **反反证**：`--plugin=no-such-plugin --out=<tmp> --logdir=<tmp> --no-shield` | **不**得退 78，须 exit 0，`--out` 指定路径**真的**收到产物，且 tracked 基线一字节未变 |

三条各自防住一件事：

- **NC21** 防"未知参数被吞"。它额外断言 `stdout` 里**没有**测量输出——
  只断言退出码的话，"跑完六分半再报错"也能过；
- **NC21b** 单独立一条，因为裸 `--out` 是**最阴的形态**：操作者写 `--out /tmp/x`，
  以为把输出重定向走了；旧代码里 `--out` 和 `/tmp/x` **两个都落空**，
  于是静默回落到覆写仓库基线。它和 `--print` 的区别是操作者**本来就有正确意图**，
  只是少打了一个等号；
- **NC21c** 是**反反证**。没有它，把检查写成"任何参数一律退 78"也能让 NC21 和 NC21b 全绿——
  那样脚本就彻底不能用了，而负控还是绿的。

**削弱反证（这才是关闭依据）**：在 `/tmp` 副本里**移除参数检查块**后重跑——
**NC21 与 NC21b 双双变红，NC21c 保持绿**。
即：这三条负控确实钉住的是这段代码，不是空转。

`selftest` 因此从 47 → **50 / 50，exit 0**（主控本轮中途实测；
最终冻结状态的权威数字见 [VERIFICATION.md](VERIFICATION.md)，仍待最终运行）。

### 0.6 这属于哪一类缺陷

与第三轮的裸 `--write-floors`（负控 NC19c）是**同一类**：

> **对无法识别的输入保持沉默，然后做一件与操作者意图不同的、破坏性的事。**

区别有两处，而且都指向"这次更严重"：

1. 裸 `--write-floors` 的后果是**该写的没写**（操作者以为下限已上调，实际一字未动）——
   是**遗漏**；本次的后果是**不该写的写了**，动的还是 **tracked 文件**——是**破坏**；
2. 上一次是"没做事"，可以靠再跑一次发现；这次是"做了错事"，
   而且产出物看起来**和一次正常测量一模一样**，不 `git diff` 根本发现不了。

**同型缺陷两轮内出现两次，说明它是系统性的，不是两个孤立 bug。**
本仓的 CLI 脚本普遍用 `args.find(a => a.startsWith('--name='))` 这种松散解析，
**每一个默认写 tracked 路径的脚本都带着同样的雷**。

建议下一轮做一次横扫：见 [§8](#8-给下一轮的建议)。

## 五、我认为本轮最该被质疑的地方（先自己列）

### 5.1 "四个代理并行改源码"这件事本身，会不会让所有测量都不可信？

**这个担心是对的，而且本轮已经真实发生过一次**——[§0.2](#02-最小复现与后果) 那次误测量
观测的正是移动靶。

现在的处置是：**最终数字必须量在冻结之后**。第三轮的做法是"所有数字量在功能改动的最后一跳，
并在分支尖端复跑确认逐格相同"，本轮沿用。

**仍然可质疑**：中途产生的任何数字（包括 [§0.5](#05-关闭依据否证不是现在绿了) 里的
`selftest 50/50`）都**不是**冻结态的数字。本文件已经把它标成"中途实测"，
但审查者有理由要求**只认冻结后的那一次**。这是一个合理的更严标准。

### 5.2 `blocked` 会不会变成"跑不动就报 blocked"的万能借口？

这是本轮最大的措辞风险。`blocked` 的正当用法是
**"环境不具备，与被测代码无关"**；不正当用法是**"我这儿失败了，先记成 blocked"**。

区分的唯一硬办法：**`blockedReason` 必须具体到能被第三方证伪**。
"Linux 不可用"不合格；"本机 `uname` 为 Darwin，`bwrap` 是 Linux 内核特性入口，
不可能存在；且 docker/podman/lima/…（逐项）均不存在"才合格——
后者任何人拿同一台机器一敲就能核对。

[COVERAGE.md §3.2](COVERAGE.md) 是按这个标准写的。**A/B/C/D 的 `blockedReason`
应当按同一标准复核**：`<待逐层复核结论>`。

### 5.3 本文件仍然是自证

和第三轮一样，这份 REVIEW 由参与者自己写。真正的独立性来自 R1 / R2 / V 三个只读复审角色。

**我建议复审者先查的地方**，按可疑度排序：

1. **[§0](#零先说一件对主控自己不利的事本轮踩了一脚破坏的是-tracked-基线) 的削弱反证有没有真的做。**
   验证办法：自己 `cp` 一份脚本到 `/tmp`，删掉参数检查块，
   用 `AGOS_SELFTEST_RUNNER` 指过去重跑——NC21/NC21b 应当变红，NC21c 应当保持绿。
   若三条全绿，说明负控根本没指到被改的那份代码。
2. **每个 `pass` 背后的替身有多宽容。** 第三轮的原话：
   *"当我修的是「调用对方的方式错了」这类问题时，替身式假对象天然会放过我，
   因为替身的宽容度由我自己写。"* 本轮 A 的 swarm 层尤其适用。
3. **每个数字能不能指到一条命令。** 本轮所有文档都按"数字必须有来源"写；
   随机抽查三个数字，问"哪条命令、哪份日志"。
